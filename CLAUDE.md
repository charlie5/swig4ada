# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Swig4Ada: a fork of SWIG 4.5.1 (4.0.0 until 2026-11-21, on the `master` branch) with an added language module (`-ada`) which generates Ada bindings to C/C++ libraries. Unusually, the Ada language module is itself written in Ada (not C++), and reaches the SWIG core through Ada bindings which were generated by swig4ada itself.

Almost all work happens in `Source/Modules/ada/`, `Lib/ada/`, `Examples/ada/` and `ada-build/`. The rest of the tree is upstream SWIG; the upstream autotools build (`configure`/`Makefile`) is not how swig4ada is built.

## Build / install

Requires GNAT + gprbuild, the GMP and PCRE2 (`libpcre2-8`) libraries, and the `gmp` Ada binding project from cBound (https://github.com/charlie5/cBound) visible on `GPR_PROJECT_PATH`.

```sh
./build_ada_swig.sh            # = cd ada-build && gprbuild -P swig_applet -Xrestrictions=xgc
sudo ./install_ada_swig.sh     # copies ada-build/swig4ada to /usr/local/bin and Lib/* to /usr/local/share/swig/4.5.1
```

- The executable is `ada-build/swig4ada` (objects in `ada-build/build/`).
- **GNAT 16 accessibility checks:** a function which returns an anonymous access type (`return access T`) gives a result whose accessibility level is that of the caller, so storing that result in a record component raises `PROGRAM_ERROR : ... accessibility check failed` at run time under GNAT 16.2 (GCC 14.2 let it through). For this reason no function in the Ada module returns an anonymous access type any more: they return named ones (`c_Type.nameSpace_view`, `c_Type.Function_view`, `ada_Type.Package_view`, `ada_Context.view`, or the package's own `View`), and call sites convert explicitly where the types differ, e.g. `ada_Package.view (the_Type.declaration_Package)`. Keep to this in new code.
- To build without replacing `ada-build/swig4ada`, add `--relocate-build-tree=<dir> --root-dir=/eden/forge` and pass the `Source/*` include directories as absolute `-I` paths through `-cargs:c` and `-cargs:c++` (the project's own include paths are relative to the object directory).
- `SWIG_LIB` is compiled in as `/usr/local/share/swig/4.5.1` (`Source/Include/swigconfig.h`). Changes to `Lib/ada/*.swg|*.i` (typemaps etc.) therefore have no effect until re-installed, unless the `SWIG_LIB` environment variable points at `./Lib`.
- `swig_applet.gpr` (C++, main is `Source/Modules/swigmain.cxx`, built with `-DADA_ENABLED`) aggregates `swig_applet_c.gpr` (SWIG core: DOH, Swig, CParse, Preprocessor) and `swig_applet_ada.gpr` (the Ada module).
- The Ada sources are compiled with `-gnatwa` plus style checks (`-gnatykp -gnatybfhi -gnatyO -gnatye -gnatyx`): no trailing blanks, no tabs, explicit `overriding`, labelled `end`s, no redundant parentheses.

## Running / testing

Invocation: `swig4ada -ada [-c++] [-I<dir>] [-outdir <dir>] [-namespace <package>] [-no-check-layout] [-debug-log] foo.i`. It emits `foo_wrap.c`/`.cxx` plus a family of `.ads` specs. With `-debug-log`, or with the environment variable `SWIG4ADA_DEBUG` set (which also catches what is done before the options are read), it writes a `swig4ada-debug.log` (the `dlog` output of the `Logger` package) into the current directory — this is the primary debugging aid, and until 2026-11-22 it was written on every run.

Generated specs depend on the support packages `swig.ads`, `swig-pointers.ads`, `swig-std_strings.ads` and `swig-guards.ads/.adb` at the repository root, and a program may use `swig-exceptions.ads/.adb` beside them, which is why scripts pass `-I../../..` to `gnatpp`/`gnatmake`. The tool itself, and cBound based projects, take `swig.ads` and `swig-pointers.ads` from cBound's `tier-0/swig` library instead, which is a separate copy: a change to a support package must be made in both places (`swig.Guards` was copied there on 2026-11-20; `std_String` was moved out of `swig.ads` and `swig-pointers.ads` into the new `swig-std_strings.ads` on 2026-11-20, and the cBound copies of those two must follow). **`swig-std_strings.ads` must not be copied to cBound:** the main program of the tool is C++, so every Ada unit of cBound's `swig` project is linked into it, and that package cannot be linked without the C++ functions of `std_string.i` (a constructor cannot be made a weak symbol). With the file there the tool does not link, and the failed link removes `ada-build/swig4ada`. cBound compiles them as Ada 2012, so they must not use Ada 2022 syntax such as square bracket aggregates. The `swigmod` builder deletes the guard specs it generates, as the tool has no use for them.

**Single example** — each `Examples/ada/<name>/` has a `builder` script, to be run from within that directory (it uses relative paths to `ada-build/swig4ada`): it cleans, generates, pretty prints with `gnatpp`, and (in most examples) builds `test_example.gpr` and runs `./tester`. A builder deletes and regenerates the specs in its directory, several of which are tracked, so expect a diff after running one. State of the examples (2026-11-21): all sixteen build and run a tester (`addlink`, `anonymous_bitfield`, `char_constants`, `class`, `enum`, `funcptr`, `import_tree`, `li_carrays`, `preproc`, `reference`, `simple`, `std_string`, `std_vector`, `template`, `typedef`, `variables`). Every tester checks its results and exits with a failure status if one is wrong, so its builder fails too. The eight which were given a tester on 2026-11-21 print each check; the eight older ones print as they always did, and say only what fails. One example does not work: `llvm` fails in SWIG's parser, which cannot read the headers of a current LLVM. Each has a `builder` and a `test_example.gpr` of the same form, differing only in the language and the interface files.

```sh
cd Examples/ada/class && ./builder
```

`Examples/ada/current_c_bug` and `current_cpp_bug` are scratch areas for reproducing the problem currently being worked on (edit `example.i`/`example.h`, run `./builder`; `./cleaner` removes generated files).

**Test suite** — `Examples/ada/testsuite` runs the generator over the upstream SWIG `Examples/test-suite/*.i` files. It needs the `lace_environ` project of the `lace` Ada library (which in turn needs `aShell` and `lib_florist`); their project directories must be on `GPR_PROJECT_PATH` (lace: every directory holding a `.gpr` under `/eden/forge/component/lace`; aShell: `/eden/forge/component/aShell/library`).

```sh
cd Examples/ada/testsuite
gprbuild -P testsuite.gpr
./launch_testsuite        # output lands in ./generated; a full run takes some ten minutes
```

- The test list is hard coded in `source/launch_testsuite.adb` as `generate ("x.i")` / `generate ("x.i", use_CPP => True)` calls, grouped by the `do_C`, `do_Cxx`, `do_uncompilable_*`, `do_broken_*` flags. The 10 commented out cases each carry a note saying why (re-checked 2026-11-20): three name a test file which does not exist, two use a library of Guile typemaps, four are inputs which SWIG itself rejects, and one (`bools.i` as C) duplicates a C++ case.  Several C++ cases sit in the C groups, with `use_CPP => True`.
- The `do_Newer` group holds the cases which upstream added between SWIG 4.0.0 and 4.5.1 and names in the lists of `Examples/test-suite/common.mk` (12 for C, 132 for C++ up to C++20). The other 49 input files which are new are for one language alone (`python_*`, `lua_*`, ...) or are parts of a case of several modules, and are not run. The `do_Older` group holds the 276 cases of those lists which were in SWIG 4.0.0 and had never been in the launcher: 273 are run, and 3 are commented out, each with its reason: `special_variable_macros`, whose input gives a class result the value of one of its members and names the types for that in each typed language but Ada; `insert_directive`, which needs a header that upstream's suite makes when it is run; and `li_std_auto_ptr`. Until 2026-11-23 sixteen more were: seven on which the generator failed, five whose specs and four whose wrappers did not compile (below). `std::auto_ptr`, which C++17 removed, is not bound, as it can be neither moved nor copied from a constant. The modules of the cases of several modules which `common.mk` lists apart (`import_share`, `import_stl`, `packageoption`) are run too, each as a case of its own, at the end of the group.
- A case whose input needs options of the generator is given them as `Options` (`generate ("command_line_define.i", Options => "-DFOO -DBAR=123 -DBAZ -UBAZ -UNOTSET")`, `-std=c23`, `-std=c++23`), as upstream's `common.mk` does. `Examples/test-suite/preproc_predefined.h` has `SWIGADA` added to its list of the symbols of the target languages.
- Some 25 cases need library files of `Lib/ada` (`std_string.i` and others), so the suite must see the current `Lib`: re-install, or run with `SWIG_LIB` set to the repository's `Lib` directory.
- To run a single test case, put a `generate (...)` call followed by `return;` at the top of the main body (check the file is not already in this state before assuming a full run) and rebuild.
- **Run-time cases** — `Examples/ada/testsuite/runtime/<case>/` holds a C++ header (`example.h`, with its functions inline), an interface file (`example.i`, whose module is named after the case) and an Ada `tester.adb`, which makes its checks through the `Checks` package of `runtime/support` and ends with `finish`. The launcher generates the binding into `runtime-build/<case>`, builds `runtime/runtime_test.gpr` with `-XCASE=<case>` (Ada and C++ both compiled with `-fsanitize=address`, so an invalid access or a leak fails the case) and runs the tester. A new case is added by a `run ("<case>")` call at the end of the launcher, with `use_CPP => False` for a case which binds C (the project is then built with `-XBOUND_LANGUAGE=C`). A case which imports a module of its own names the interface file of that module (`Imported => "base"` for `base.i`), which is generated first. The 38 cases of its own (2026-11-25, 1071 checks; with the 46 of upstream's suite, below, 84 cases and 1425 checks): `values`, `class_values`, `virtual_classes`, `mutual_classes`, `containers`, `exceptions`, `namespaces`, `overloads`, `c_library`, `smart_pointers`, `imports`, `extensions`, `templates`, `multiple_inheritance`, `nested`, `callbacks`, `arrays`, `constants`, `static_members`, `layouts`, `strings`, `directives`, `derived_layouts`, `moves`, `in_namespace` (generated with `Options => "-namespace outer"`, with the package `Outer` in the folder of the case), `warnings`, `library` (a multiset, a multimap, a complex number, a wide string and the streams), `library_c` (in C: `typemaps.i`, `cdata.i`, `argcargv.i` and `file.i`), `directors` (virtual functions which Ada cannot call through the vtable, overridden in Ada through a director), `virtual_bases` (classes which inherit a base class virtually), `leveldb`, `pugixml`, `taglib`, `jsoncpp`, `yamlcpp`, `tinyxml2`, `bullet` and `assimp` (below). A case which binds a library of the system names it (`Library => "leveldb"`), and its tester is linked with it (`-XLIBRARY=` of `runtime_test.gpr`); a library which is several names the others too (`Also_Link => "BulletCollision,LinearMath"`, `-XLINK=`), and one whose headers name each other from their own folder gives the C++ compiler that folder (`Cxx_Options => "-I/usr/include/bullet"`, `-XCXX_OPTIONS=`). A case is given further options of the generator by `Options`. A failure leaves `generated/<case>-runtime.log`. Anything which C++ calls back (an Ada function given as a callback, a class derived in Ada from a C++ class) must be declared at library level, not inside the tester.
- The wrapper of every case checks the layout of each of its classes (see the layout checks, below), which is the default: 761 assertions over the suite. A case whose input is made so that a record cannot match (`typedef_struct`, `typedef_struct_cpp` and `director_property`, each of which hides a member from SWIG, and `nested_class`, which shows SWIG a member that the compiler is not shown) is given `check_Layout => False`, which generates it with `-no-check-layout`.
- Baseline of the specs and the wrappers (`check_against_Baseline`, under the `check_Baseline` flag): either may change and still compile, so after the compile check the launcher compares each generated spec and wrapper file with the one which was last accepted. `baseline.sha` holds a checksum of each and is tracked; the files themselves are kept in the `baseline` folder, which is not. A file which is changed, new or gone is counted (`Files which differ from the baseline`), listed in `generated/baseline-changes.log` (with its differences, where the `baseline` folder is present) and fails the run. `./launch_testsuite accept` makes the specs and wrappers of the last run the baseline, and is run once the changes have been looked at and are as they should be; commit `baseline.sha` with the change which caused them. It does not run the suite again (until 2026-11-22 it did): each run notes how it ended (`generated/last-run`) and a checksum of the tool and of every file of its library (`generated/last-run.tool`), and `accept` refuses where the last run was of a part of the suite, failed in more than its differences from the baseline, or was made with another tool or library (so `SWIG_LIB` must be as it was for the run). The specs are pretty printed, so another version of `gnatpp` may change them all.
- Two further checks are counted with the unit tests (`run_Step`). `check_the_layout_Assertions` shows that a layout check can fail: `runtime/wrong_layout` hides a member of a structure from SWIG, and the launcher requires that its wrapper does not compile, with the message of the assertion, and that it does with `SWIG_ADA_NO_LAYOUT_CHECKS` defined. `check_the_Bootstrap` generates the three bindings of the tool to the swig core again, into `unit-build/bootstrap`, and requires each spec and wrapper to be as it is in `Source/Modules/ada/swig_binding`; a change to the tool which changes them fails here until the bindings are regenerated and committed.
- `check_the_imported_Symbols` (also a `run_Step`): the cases are compiled and never linked, so a symbol which a spec imports and which does not exist was never seen. Each wrapper is compiled to an object (a C++ one with every inline function kept, `-fkeep-inline-functions`; into `unit-build/symbols`), and each symbol which a spec imports (a function of the wrapper, a variable of the library, a C++ symbol which the tool makes) must be one which some object defines or refers to. Those which are in none must be the lines of the tracked file `expected-missing-symbols` (18 of some 11,500): a constant member with a value which is not worked out, which C++ gives no symbol unless it is defined outside its class; a member of a variadic template instance; the standard streams, which are in the C++ library; `unbound`, the place holder of a virtual function which is not bound; the function of `dynamic_cast`, whose wrapper does not compile; and what the inputs declare and never define. When the check was first made (2026-11-22) some 250 were missing, and most were faults of the tool, since corrected.
- Reading the differences of a run: most break nothing, so `./baseline_report` (a Python script, which the launcher runs whenever the baseline differs and the `baseline` folder is present) picks out those which may break a program that uses a binding, and writes them to `generated/baseline-report.log`: a package which is now seen through a limited view, or no longer is; a declaration which is gone; a subprogram, variable, type or record component which has changed, with what it was and what it is. **Read that report before `./launch_testsuite accept`.** (On 2026-11-22 a baseline was accepted on a summary of its differences, and held a fault which cBound then showed.)
- cBound (`./check_cbound`, the last step of the launcher, under the `do_cBound` flag): cBound is the one user of the tool which is at hand, and is otherwise tried only once the tool is installed. The script copies it into `unit-build/cbound` (its own folder is left as it is; it is found by the environment variable `CBOUND`, or as `component/cBound` beside the `applet` folder, and the step is passed over where it is absent), generates each binding of the copy again with `ada-build/swig4ada` and the `Lib` of the repository, and runs cBound's own `./check_all`. A binding which cannot be generated, or a step which fails, fails the run. The files which are generated differently are listed, with their differences in `generated/cbound-changes.log`, and are no failure: they are what a commit to cBound will hold once the tool is installed.
- At the start of a full run the launcher removes the specs and wrappers of the run before (`generated/*.ads`, `*_wrap.*`). Until 2026-11-22 it did not, so a spec which was no longer generated stayed, was compiled and counted, and was never seen to be gone.
- `./check_links` (a `run_Step`, after the check of the symbols, whose objects it uses): for each case it builds, links and runs a program which does no more than `with` every spec of the case. A spec is otherwise only compiled for its meaning (`-gnatc`); here its code is generated, its packages are elaborated, and whatever it refers to (the constructor which the initialisation of an imported C++ type calls, the functions of a support package) must be in the wrapper of the case or in the C++ library. All 773 take some 25 seconds. A case which imports another module is linked with the wrapper of that module too (the modules which its specs name in their context, and those which they import in turn), where its own wrapper does not serve alone: two modules whose inputs include one header may each define what it holds, and cannot be linked together. The cases which fail must be the lines of the tracked file `expected-link-failures` (1): `virtual_derivation`, whose input declares a constructor which it does not define. (Requiring each imported symbol to be defined by the wrapper of its own case, as a linker does, was measured first and found nothing which the check of the symbols had not.)
- Cases of upstream's suite as run-time cases (`run_Upstream ("<case>")`): the input is `Examples/test-suite/<case>.i` and the tester, which is written after the test that upstream has of the case for Python (`Examples/test-suite/python/<case>_runme.py`), is `runtime/up_<case>/tester.adb`, with an `expected-warnings` file where the case warns. The 46 of 2026-11-24 (354 checks): `using_inherit`, `ret_by_value`, `return_const_value`, `typedef_scope`, `struct_initialization`, `constover`, `global_vars`, `cpp_enum`, `smart_pointer_member`, `cpp_static`, `primitive_ref`, `virtual_poly`, `template_inherit`, `typedef_inherit`, `unions`, `varargs`, `operator_overload`, `cpp_namespace`, `voidtest`, `friends`, `li_std_pair`, `member_pointer`, `namespace_class`, `overload_simple`, `overload_subtype`, `smart_pointer_simple`, `smart_pointer_overload`, `using_extend`, `using_private`, `using_protected`, `abstract_access`, `array_member`, `template_ns`, `inherit_missing`, `constructor_copy`, `enum_template`, `typedef_class`, `extend_template`, `smart_pointer_rename`, `static_const_member_2`, `template_extend1`, `template_rename`, `enums` (as C), `cpp11_alternate_function_syntax`, `template_default_arg` and `cpp11_using_member_template`. The first eleven found five faults of the tool, the next eight one (a typedef which the module is not told of), the next five one (pointers to members), the next eleven three (below) and the last ten none; upstream has such a test of some 400 cases. `minherit` is not one of them, as its input is for the languages which have multiple inheritance. An input may leak of itself (the constructor of `varargs` keeps a string which nothing frees), and its tester then tells the check for leaks to pass over that (`__lsan_disable`). Where upstream's test calls a function which a derived class inherits from a base with no virtual function, the Ada tester names the base (`Foo.test (Bar.as_Foo (the_Bar).all, 3)`), as such a base is a part of the record, unless a `using` declaration names the function in the derived class.
- `./check_vtables` (a `run_Step`, a Python script): a tagged type of convention CPP has a place in its vtable for each of its primitive subprograms, in the order in which its spec declares them, and that must be the order in which C++ lays out the virtual functions of the class. Where it is not, nothing fails to compile or to link: a dispatching call reaches another function. The script has the compiler write the layout of each vtable (`g++ -fdump-lang-class`, run on each wrapper, into `unit-build/vtables`), takes the primitives of each tagged type from its spec (those of its parent first, an override in the place of what it overrides), and compares them place by place: the number of places, and the name in each where both have one (a destructor, a pure virtual function, a place holder and an operator are not compared by name). It covers the 757 classes with virtual functions of the suite in under a minute. A class is known by its C++ name from the function of the wrapper which destructs it (`Ada_delete_<name>`), or, where its destructor is not public, from the functions of the wrapper which its spec imports and which take the object first (`X *arg1`, set from `a_arg1`), the one which most of them take (2026-11-25; until then such a class, tinyxml2's nodes among them, was passed over, and 682 were compared). The classes which differ must be the lines of the tracked file `expected-vtable-differences` (12): a function which the interface file renames has another name in the same place (10); and a class whose input hides a virtual destructor from SWIG (2). A primitive of the name of one of the parent overrides it where its parameters are, or may be, of the same types; two types of `interfaces.C` which are named differently are not, so an overload which a derived class adds (`label (double)` beside `using Base::label;` of `label (int)`) has a place of its own (until 2026-11-23 the script took it for an override, and reported the one class of the suite which has such an overload). When it was first run (2026-11-23) 51 differed, of which 27 in the number of their places. Given a folder and the options of the compiler, it checks another binding, which must have no difference: the launcher runs it so on the tool's own binding of the swig module (`swig_binding/swigmod`, the classes `Language` and `Dispatcher`), where the fault of 2026-11-23 was, and which it finds in that binding as it was before the fix.
- `./check_calls` (a `run_Step`, a Python script): whether C++ constructs a class decides how it is passed and returned, and so whether it is bound as a limited record of convention CPP or as a plain record. Where the tool takes a class for the other kind, nothing fails to compile or to link: a constructor leaves the object of the caller as it was, or a result is sought where C++ has not put it. The script takes the kind of each class from its spec and has the compiler say, by an assertion which is compiled after the wrapper of the case (into `unit-build/calls`): a class is not trivial for the purposes of calls, as the Itanium C++ ABI has it, where its destructor or the constructor by which it is copied or moved is not trivial, or where it can be neither copied nor moved. It covers the 2,808 classes of the C++ cases in a few seconds. A class is known by its C++ name as in `./check_vtables`: from the function of the wrapper which destructs it, or, where its destructor is not public or is deleted, from the functions of the wrapper which its spec imports and which take the object first (2026-11-25; until then 2,778 were asked of, and tinyxml2's nodes were not). The classes which differ must be the lines of the tracked file `expected-call-differences` (8): a class whose base class, or a member, is one which SWIG is never shown, so that the tool cannot know (4: `HiddenDerived1` twice, `Person` with a `std::string` and no `std_string.i`, and `SquareFunctor`; `E1` of `std::exception` agrees since `std_except.i` declares its base, 2026-11-24), and a class with a member which is an rvalue reference and an assignment operator of its own, which C++ can then neither copy nor move (4). When it was first run (2026-11-23) 61 differed. A class with a deleted destructor and no function of the wrapper is not asked of, as nothing names it. Given a folder and the options of the compiler, it checks another binding, which must have no difference: the launcher runs it so on the tool's own binding of the swig module (`Language` and `Dispatcher`). cBound's bindings have nothing for either compiler-backed check to compare (looked at on 2026-11-23): those of opencv, speech_tools and festival bind functions and opaque pointers, with no class, and that of gmp binds C structures.
- The warnings of a run-time case are checked: those numbered from 861 must be the lines of the file `expected-warnings` of the case (each less the folder of its file), and a case with no such file must give none. `multiple_inheritance`, `strings`, `warnings` and `virtual_bases`, among others, have one.
- Unit tests (`run_Unit`, under the `do_Units` flag): `unit/<unit>` holds `<unit>_test.gpr` and a main program which tests one unit of the Ada module apart from the tool, with the `Checks` package of `runtime/support`; the launcher builds it into `unit-build/<unit>` and runs it, and a failure leaves `generated/<unit>-unit.log`. There are three. `mangling` (56 checks) makes the C++ symbol of each name of a table (classes and variables in namespaces and classes, and template instances whose arguments are standard types, classes, pointers, references and integers, 15 of which need a substitution) and checks it against the symbol which GCC gave, and that a name which is not dealt with is given no symbol. `expressions` (76 checks) works out a table of C expressions (numbers in each base, characters, every operator and its precedence, `sizeof`, names with and without a namespace) and checks each against the value which GCC gave, and that what cannot be worked out is refused. `layout` (31 checks): it makes records by hand and checks the place which `ada_Layout` gives each component, for a plain structure, bit-fields, a base class whose tail is used, a base which is a plain structure, and a class of an imported module. The places it expects were taken from GCC.
- The launcher makes four checks of each case: the generator exits without error; `gnatpp` finds no syntax error in the specs; the wrapper compiles (`gcc -std=gnu17 -fsyntax-only`, or `g++ -fno-access-control -fsyntax-only`); and, once every case has been generated, the specs compile (`gcc -c -gnatc -gnat2022 -I<repository root>`). It then runs the builder of each of the sixteen examples of `Examples/ada` (`run_Example`, under the `do_Examples` flag), which regenerates the example's binding in its own directory, builds its tester and runs it; a failure leaves `generated/<example>-example.log`. It prints a count of each kind of failure, of the run-time cases which fail and of the examples which fail, and exits with a failure status if there is any. A failure leaves `generated/<case>-generator.log`, `-pretty_print.log`, `-wrapper.log` or `-compile.log`. Only the run-time cases are linked and executed. The wrappers are written into `generated` too, so `do_tidy.sh` is no longer needed.
- `-fno-access-control` is used because the Ada module wraps protected members, and such a wrapper compiles only where access is opened to it (`swigmod.i` does so with `#define protected public`). Without the switch the wrappers of eight further cases do not compile.
- A case whose wrapper is known not to compile is given `wrapper_Compiles => False` and a note of the reason (1 case: `dynamic_cast`, whose input sets a member of a type descriptor at file scope, where Ada has no initialisation function); the launcher says when such a wrapper has begun to compile.
- Baseline (2026-11-24, SWIG 4.5.1): 774 cases (758 on 2026-11-22: `multi_import_d` was added, as `multi_import_b` now imports it, then the 144 cases of the `do_Newer` group and the 264 of the `do_Older` group; then the sixteen of that group which were made to run on 2026-11-23), with no failure of any of the four kinds, 77 run-time cases, 12 unit tests and checks and 16 examples, none of which fails. For a case which `%import`s another module, the specs of that module must be on the search path, which the single `generated` directory provides (`clientdata_prop_b` needs `clientdata_prop_a`, `imports_b` needs `imports_a`, `mod_b` needs `mod_a`, `multi_import_a` needs `multi_import_b`, `template_typedef_import` needs `template_typedef_cplx2`).

## Architecture

### C++ / Ada bridge

- `swigmain.cxx` registers `{"-ada", swig_ada, ...}` and calls `adainit`/`adafinal` around SWIG's main. `swig_ada` is exported from `ada_language.adb` and returns the address of an `ada_Language.item` built by `ada_Language.Forge.construct`.
- Updating the core to a later SWIG (done for 4.5.1 on 2026-11-21): replace every upstream file, remove those which upstream has dropped, and apply the local changes again. ### Pipeline (see `Doc/Ada/swig4ada_pipeline_dfd.png`)

1. **Collect (C model)** — during `do_base_Top`, the handlers in `ada_language.adb` build a language neutral model of the C/C++ declarations: `c_Type` (a variant record discriminated on `a_c_type_Kind`: `Unknown`, `Typedef`, `c_Class`, `function_Pointer`, ...), `c_Function`, `c_Variable`, `c_Parameter`, `c_nameSpace`. They are gathered per SWIG module into a `swig_Module.item`, which pairs a `c_Module` with an `ada_Module`; `%import`ed modules get their own entries (`new_Modules`), separate from `Module_top`. The handlers also emit the C wrapper functions (named `Ada_%f`) into the `_wrap` file. `ada_Language.c_expression_Resolver` evaluates C constant expressions (using GMP) so they can be emitted as Ada constants.
2. **Resolve / prune** — `process_all_Modules` resolves `Unknown` types which turn out to be function pointers, and `prune_unknown_C_Types` drops whatever remains unknown, along with any declaration depending on it. (Without this step an unresolved type reaches the transformer and raises `CONSTRAINT_ERROR ... key not in map`, as `template_typedef_cplx2` shows.)
3. **Transform (Ada model)** — `Transformer.transform` maps each `c_Module` into an `ada_Module`, populated with `ada_Package`, `ada_Type` (a tagged hierarchy under `ada_type/` mirroring the Ada RM type classification: elementary/scalar/discrete/..., composite/record/array, access-to-type/subprogram), `ada_Subprogram`, `ada_Variable` and `ada_Parameter`. Imported modules are transformed before the main module.
4. **Generate** — `ada_Language.source_Generator.generate` writes the `.ads` files from the Ada model, after which `top` dumps the C runtime sections into the `_wrap` file.

A class may have any number of members: the components of a class of the C model, and of a record of the Ada model, are kept in storage which grows (`make_Room`), and what a declaration depends on is gathered in a vector. A pointer is hashed by `pointer_Hash`, a generic function, not by an unchecked conversion to the hash type.

The lookup maps tying the two models together (`name_Map_of_c_type`, `c_type_Map_of_ada_type`, `c_namespace_Map_of_ada_Package`, ...) live in the `ada_Language.item` record and are instantiated in `swig_Module`.

### Reference: `g++ -fdump-ada-spec`

GCC has its own C/C++ to Ada spec generator: `g++ -c -fdump-ada-spec -fsyntax-only foo.h` writes `foo_h.ads`. It binds directly to the mangled C++ symbols, with no wrapper file, and is a useful reference for how GNAT expects C++ constructs to be imported. Consult it when deciding how the Ada module should map a C++ construct. Points of comparison (checked 2026-11-20, GCC 16.2):

- A class with only pure virtual functions is an `abstract tagged limited record`, not an interface — as here.
- Every member function is imported by an aspect on its declaration (`with Import => True, Convention => CPP, External_Name => "..."`), and each constructor has its `pragma CPP_Constructor` directly after its declaration — as here for overloads in a virtual class. Its constructors return the type itself, where the Ada module returns `Item'Class` for a virtual class.
- A virtual destructor is two primitives: `Delete_X`, importing the complete object destructor (`D1`), and `Delete_And_Free_X`, importing the deleting destructor (`D0`). The Ada module's `destruct_0` and `destruct` are the same pair, under different names.
- It is not an oracle: its output for a class hierarchy with a pure virtual destructor does not compile (the per-class `Delete_X` names do not override one another), and for multiple inheritance it emits `new C and AA`, which GNAT rejects unless `AA` is an interface.

### Shape of the generated output

For a module `foo` (see `ada_module.ads`):

- `foo.ads` — top package, containing the simple types, constants and global variables. A global variable whose type is a class, or lives in the pointers packages, is declared in `foo-binding.ads` instead, as the top package cannot see its own children. A constant pointer to a function (`%constant UnaryOp *NEGATE = negate;`) is also declared there, as a deferred constant completed at the end of the private part (`the_NEGATE : aliased constant foo.UnaryOp_pointer := negate'Access;`), since taking the access of the function must follow its import pragma. A variable which differs only in case from an enumeration literal or a function of the package is given a `the_` prefix (C `enum E {slap} Slap;` gives `the_Slap`), still importing the C symbol. Likewise an enumeration literal which differs only in case from the name of its own type (C `enum Hello {hi, hello};` gives `the_hello`).
- `foo-binding.ads` — the imported (non-class) C functions.
- `foo-pointers.ads`, `foo-pointer_pointers.ads` — pointer and pointer-to-pointer types.
- `foo-<type>.ads` — one child package per struct/class (and per function pointer type). A class with the name of its module is given the package `foo.c_foo`, as a package `foo.foo` would hide the module within itself (`ada_Package.ada_Name` gives the name used in the Ada source; the plain `Name` is still used to build mangled C++ symbols). A typedef of a class (`typedef Engine PersEngine;`) also gets a child package, whose `Item`, `Item_Array`, `Pointer`, `Pointer_Array` and `Pointer_Pointer` are all subtypes of those of the class, so the two may be used interchangeably, as in C++.
- In a virtual class package, each overloaded member function is imported by an aspect on its own declaration (`with Import, Convention => CPP, External_Name => "..."`), and each overloaded constructor has its `pragma cpp_Constructor` directly after its declaration. Elsewhere an overload is imported under a unique `_vN` name in the private part and the public name renames it; that cannot be used in a virtual class, where the `_vN` twin would be a further primitive with a vtable slot of its own.
- A C++ class with only pure virtual functions and no data is modelled as an abstract tagged type, not as an Ada interface (`is_interface_Type` always returns False). An interface is laid out as a secondary base, which matches C++ only for a second or later base class, and multiple inheritance is not supported.
- Base classes of a virtual class: the first base class which is itself virtual, and is not inherited virtually, becomes the parent of the tagged type, as C++ places it first in the object (for a virtual base, see the classes which inherit a base class virtually, below). A base class which is not virtual becomes a record component (`class D : Plain, Poly` gives `type Item is new Poly.item with record Plain : aliased Plain.Item; ... end record`). Any further virtual base class is dropped with a warning (`Warning: the base class 'B' of class 'C' is ignored, ...`), as SWIG's C# and Java modules do: members inherited through it are absent from the binding, a function which overrides one of them is emitted without `overriding`, and an object is laid out correctly only as seen through its parent. A class with no virtual members has every base class as a record component (but see the layout of derived classes, below).
- Imported modules (`%import`): only the specs of the main module are written; those of an imported module come from that module's own run. The core hands on no member of an imported class, as nothing of that module is wrapped. Its member variables are collected all the same (`collect_the_Members_of_an_imported_Class` of the class handler, which gives each node of a member variable to `memberVariableHandler`, with the hidden members as for any class), so the layout engine lays such a class out as any other: a class of the main module which is derived from it uses the tail of its base where C++ does, has a representation clause where it needs one, and has its layout checked in the wrapper; and a base with no members takes no room. No wrapper function is made for a member of an imported class. (Until 2026-11-23 the layout of an imported class was taken to be not known, `laid_Out` returning False for a record of another module: a class derived from one was laid out as GNAT would, with a warning and no check, so a member which C++ has in the tail of the base was out of its place. Before 2026-11-22 an imported class was taken for a class with no members, so the record of the derived class lost its base altogether.) Its virtual functions are collected too, by `memberFunctionHandler`, so that a function of the main module which overrides one takes its parameter and result types as it does within one module (`const int&` for `const Paces&`, a `Horse*` result for an `Animal*`; before, the spec of such a class did not compile). `functionWrapper` returns at once for a node of an imported module, so no function of the wrapper is made; it tells the module by the node which it is given, as `current_Module` is worked out from `current_c_Node`. Its other member functions are not collected, nor its destructor (a destructor of the main module overrides on the word of `has_virtual_Destructor`). A `using` declaration which names a function of an imported base is followed all the same, as the core gives the function with the declaration (until 2026-11-24 a constant one was passed over, of any base, as `usingDeclaration` took the declarator of a function to begin `f(`, where that of `int total () const` is `q(const).f().`; the `imports` run-time case has both). A node which the core has not handed on is as the parser left it, with its declarator apart from its type (`int` and `p.` for `int *p;`, `Animal` and `f().p.` for `Animal* self ();`): the step joins them for the time of the call, as the core's `cDeclaration` does. The member functions of an imported class are not collected, so whether a class is virtual is noted from its declaration (`c_Type.has_virtual_Members`). A class declared in an imported module but defined in the main module gets its package in the main module (`mod_b.C` for a `class C;` declared in `mod_a`). A base class is always named by its full package name, as it may be in another module.
- A function whose return type or a parameter type has no Ada type (an unresolved type, such as a typedef nested in a class template) is left out of the binding, with a warning in the tool's output. When it is a virtual function which does not override, a primitive `unbound_virtual_<n> (Self)` is declared in its place, so that the vtable slots which follow keep their position; it must not be called.
- Names: a class template instance with no name of its own (`A<int>`, which SWIG writes as `A<(int)>`) has its template and argument names joined into an identifier (`A_int`). Two classes or typedefs whose names differ only in case (`hi0` and `Hi0`) would share a package and a file, so the later one is given a numeric suffix (`Hi0_2`).
- Overriding: a function which overrides takes the result type of the function it overrides, as C++ allows a covariant result (a pointer to a derived class) where Ada requires the same type. An override of a function which could not be bound is left out, with a warning. A class with no base class overrides nothing (a smart pointer class is given the functions of the class it points to, marked as overriding).
- An empty union is declared as a plain null record.
- Mutually dependent classes: when class `A` has a pointer to class `B` as a parameter or result, and a subprogram of `B` has a parameter or result of a type of `A`, the specification of `A` has only a limited view of `B` (`limited with foo.B;`), and names the pointer as `access foo.B.Item` in place of `foo.B.Pointer`. Two specifications cannot `with` each other. Only this direct, two package cycle is recognised.
- Anything in the top package whose type is declared in a child package of the module is declared in `foo-binding.ads` instead (a variable which is an array of, or a pointer to, a class, for example). A typedef of a pointer typedef gets a child package, like a typedef of a class typedef.
- A type or child package whose name differs only in case from that of another type or child package of the same package is given a numeric suffix (`uint64` and `UINT64` give `uint64` and `UINT64_2`). The array of a type is named after the Ada name of the type.
- A real constant whose value is beyond the range of its type (`#define HUGE_VAL 1.0e10000`, which C takes as infinity) is left out, with a warning. A generated spec uses no Ada 2022 syntax, as a binding may be compiled as an earlier Ada (cBound's gmp test is compiled as Ada 2005): an aggregate is written with parentheses.
- A constant whose value is the size of a C type (`sizeof(int)`) is given the size of the Ada type (`interfaces.c.int'Size / interfaces.C.char'Size`). An array variable of unknown length is declared with the bounds `0 .. interfaces.C.size_t'Last`.
- The declarations of a file imported with no module name (`%import "foo.h"`) are bound along with those of the main module.
- Type registration (`ada_Language.register`): a type is known by its swig type and, for convenience, by its unqualified name and the names of its array, pointer and reference types. Two types of different scopes may share such a name (an enumeration of the same name in each of two classes); the name then stays with the first, and registering a swig type a second time does nothing. A lookup of a swig type which may be missing goes through `demand_c_Type_for`, which makes an `Unknown` type for the prune step to deal with.
- Warnings (`Logger.warn`, `c_Declarable.warn`): a warning is given through the core's `Swig_warning`, so it has a number, names the file and line of its declaration, and can be turned off (`-w861`, `%warnfilter (SWIGWARN_ADA_NOT_BOUND) name;`). There are four, declared in `Source/Include/swigwarn.h` (a local change to the core; `Lib/swigwarn.swg` is made from it by the `sed` command of upstream's `Makefile.in`): 861 `WARN_ADA_NOT_BOUND` (a declaration is left out), 862 `WARN_ADA_LAYOUT` (a record may not match its class), 863 `WARN_ADA_VALUE` (a value could not be worked out, and another is used) and 864 `WARN_ADA_UNSUPPORTED` (no longer given: its uses, pointers to members and virtual inheritance, are now bound). Each handler notes where it is (`locate`, wherever `current_c_Node` is set), and a declaration of the C model keeps the place at which it was made, with the warnings which the interface file turned off there (`c_Declarable.Item`), so that a warning of the later steps (prune, transform) is still about the right line. A warning about no declaration names the interface file. New code gives a warning by `warn`, never by `log ("Warning: ...")`.
- Whatever cannot be bound is left out with a warning in the tool's output, rather than raising: a base class which is not known (ignored, or a template never instantiated), a member, variable, array or pointer whose type has no Ada type, an overload which cannot be told apart in Ada. A record which loses a base class or a member no longer matches the layout of its class, and the warning says so.
- C expressions (`ada_Language.c_expression_Resolver`): a number which begins with a zero and has more digits is octal (`0755` is 493; until 2026-11-22 it was read as decimal, so that an array `int a[010]` had ten elements), and a number may be hexadecimal, binary (`0b110`) or a character within its quotes (`'A'`, `'\n'`, `'\x43'`, `L'\0'`, which is the number of its position; a lone letter with no quotes is a name, and was once taken for a character, so that an enumeration value which is a character is now right: it was given the next value in sequence); the operators are the arithmetic ones with `%`, the shifts, the bitwise and logical ones and the six comparisons, which give 1 or 0. They are applied as C applies them (`Result_of`): those of one sign first, from the right, and then each level of precedence in turn (`* / %`, `+ -`, the shifts, the comparisons, `== !=`, `&`, `^`, `|`, `&&`, `||`), from the left within a level. (Until 2026-11-22 each operator was reduced in a pass of its own, in an order which was not C's: `1 - 2 + 3` gave -4, and `1 + 2 << 3` gave 17.) A character literal of several characters (`'ab'`) is the integer which GCC makes of it, the first character highest; a `float` literal loses its suffix (`4.0f`); and a constant whose value is a three way comparison (`<=>`) is left out, with a warning. A string constant is given as the text which it stands for (the core's `stringval`), with a quote doubled and a control character joined in by its position, so an escape or a raw string literal is right. A real literal is made one of Ada (`12.` is `12.0`, `10E1` is `10.0E1`). A numeric constant whose value cannot be worked out is given as it is written only where that is made of numbers and of constants of the module (`is_plain_Expression`); otherwise it is left out, with a warning, as is a constant whose value is the address of an object or an object of a class. `true` and `false` are 1 and 0, `sizeof` of a standard C type is taken from `interfaces.C` on the generating machine, and a `U` or `L` is a literal suffix only directly after a value. An enumeration value which cannot be evaluated (one depending on a template parameter) takes the next value in sequence, and an array dimension which cannot be evaluated makes the length unknown; both are warned of.
- `%insert("begin")` text goes to the runtime section of the wrapper, there being no separate begin section.
- Typedefs: one declared in a class, of a type of that class which is neither a class nor a pointer (`struct T { enum trees {...}; typedef trees treestd; };`), is a subtype in the package of the class. Any other typedef of a type declared in a child package gets a child package of its own, as does a function pointer type with a parameter or result declared in one.
- No array of, or pointer to, an unconstrained array type (`typedef char namea[];`) is declared, as neither an array nor `interfaces.C.Pointers` can have an indefinite element.
- A constant of an enumeration type whose value is known as a number is given by representation (`Hello'Enum_Val (1)`). A constant which is a pointer to a class member is a constant object of the wrapper, imported as a constant (below). A constant of a type which C++ constructs is left out, with a warning (`%constant std::string MY_STRING = "OK";`), which has neither a symbol nor a value which Ada can give.
- Library files (`Lib/ada`): the C++ standard library classes are bound like any other class, so each `std_*.i` declares the data members of the GNU libstdc++ implementation ahead of the member functions, giving the Ada record the layout of the C++ object (`std_vector.i`, `std_list.i`, `std_deque.i`, `std_set.i`, `std_multiset.i`, `std_map.i`, `std_multimap.i`, `std_pair.i`, `std_complex.i`, `std_wstring.i`, `std_function.i`, and `std_stack.i`, of its default container, whose members are those of the deque which it holds; 2026-11-24). `std::string` is the exception: it is a type of the support package `swig.std_Strings` (see below), and `std_string.i` makes it known and supplies the functions which that package imports. The streams (`std_iostream.i`, `std_sstream.i`) are incomplete classes, usable by reference only; each is an instance of a template which is declared and not defined (`template <class CharT, class Traits = char_traits<CharT> > class basic_ostream;`), named by a typedef (`typedef basic_ostream<char> ostream;`), so that the core takes a stream which a header names as an instance (`std::basic_ostream<char, std::char_traits<char> >&`, as pugixml has them) for the typedef, and both are one incomplete class (2026-11-25; until then the file declared `class ostream;`, which nothing named so took for the same type, and pugixml lost some 50 declarations). `std_map.i` declares the iterators of a map as GNU libstdc++ has them (`std::_Rb_tree_iterator<std::pair<const K, T> >`, of one member, the pointer to a node, and its `const` twin) and the typedefs `iterator` and `const_iterator` of the map, so that a class with a member which is the iterator of a map (jsoncpp's `ValueIteratorBase::current_`) has its layout; the instances must be named with `%template`. `stl.i` includes those of the string, the vector, the map and the pair, as that of the other languages does (the generic one, which was used until 2026-11-23, declares nothing and warns that it is not implemented). `factory.i` and `implicit.i` accept their directives and do nothing, as Ada needs neither; `file.i` makes `FILE` an opaque structure.
- A member variable added by `%extend` (as `%attribute` does) is not a data member, and is not made a record component.
- Wrapper file: a member function is called as `arg1->Class::f()`, where the class is named as C++ knows it (`Base< int >`, not the name it is bound by). A class returned by value is held in a `SwigValueWrapper`, so it needs neither a default constructor nor assignment. The construction function of a class (`ada_new_...`, which returns the object by value) has a name made of identifier characters only, and is left out where the destructor is not public or the constructor was added by `%extend`. A constant reference to a primitive type is a pointer on both sides, bound straight to the object of the caller.
- Exceptions: a C++ exception caught by a `throws` typemap, a failed `%contract` and `SWIG_exception` do not raise an Ada exception. They record a pending exception (`adahead.swg`), which the support package `swig.Exceptions` reads: `is_Pending`, `pending_Kind`, `pending_Message`, `clear`, and `check`, which raises `swig.Exceptions.Error` with the message of the C++ exception and forgets it. The caller decides when to check; generated code does not. With `%include <std_except.i>` a standard exception is recorded by its kind and with its own `what ()`; without it the message only names the type. `Lib/ada/std_except.i` (2026-11-24) has the `throws` typemaps of the generic file, which uses `SWIG_exception`, and declares the standard exceptions as classes with the shape of GNU libstdc++, where the generic file declares each an empty structure, ignored: `std::exception` (bound as `the_exception`, as `exception` is a reserved word; warning 314 is filtered) has a virtual destructor and `what`, `std::logic_error` and `std::runtime_error` add their message, a `__cow_string` of one pointer (a private `void*`), and `bad_cast`, `bad_exception` and the six others derive from these, with constructors from a `char*` alone, so that the file needs no `std_string.i`. Each destructor has a body, so that it is made by a function of the wrapper. A class which is derived from one of them is laid out and dispatches as any other: until then such a class had a base which SWIG was never shown, so that its layout was not checked and its virtual functions were called through their wrappers (jsoncpp's `Exception`, `RuntimeError` and `LogicError`, and pugixml's `xpath_exception`, whose interfaces now include it, and lose four warnings). pugixml's interface includes `std_iostream.i` and `std_wstring.i` too. A string which a header names as an instance of the template (`std::basic_string<char>`, `std::basic_string<wchar_t>`, with its traits and allocator or without them) is sought as the class which the module knows it by, `std::string` or the `wstring` of `std_wstring.i` (`as_a_standard_String`, which `demand_c_Type_for`, `typedefHandler` and `returns_a_cpp_constructed_Type` ask; 2026-11-25). Until then pugixml's conversions to and from wide strings were left out, and its `string_t` (`std::basic_string<char>`) was an opaque type, so that `as_utf8`, which returns one by value, was an Ada function which returned a plain record where C++ returns the string through a hidden pointer; each is now a procedure with a `Result`, and the tester converts a string to a wide string and back. The `exceptions` run-time case checks a class derived from `std::runtime_error` and one from `std::exception`: their sizes, a member after the base, and `what` called through the vtable from C++ and from Ada. Like `swig.std_Strings`, the package imports functions of the wrapper, so it must not be copied to cBound. The symbols `SWIGADA` and `SWIGAda` are defined for conditional compilation.
- Classes which C++ constructs: a class which declares a destructor or a copy constructor, or has a base class or a member which does (a `std::string` member among them), is passed and returned by C++ through a hidden pointer, so it cannot be a plain record. It is bound as a limited record imported with convention CPP (`type Item is limited record ... end record; pragma Import (CPP, Entity => Item);`), as a virtual class is, but is not tagged. Each of its constructors has a `pragma cpp_Constructor` directly after its declaration (GNAT 16 crashes on the renaming of such a function, so the `_vN` scheme is not used), and its `Pointer` is `access all Item`, as `interfaces.C.Pointers` takes no limited element. Ada code cannot copy or assign such an object; an object declared with no initial value is given its default constructor by GNAT. `ada_Type.composite.a_record.is_Nontrivial` and `is_constructed_by_Cpp` (virtual or not trivial) and `ada_Package.models_a_constructed_cpp_Class` are the tests; a union is never one. The core records a declared destructor or copy constructor on the class node (`allocate:has_destructor`, `allocate:has_copy_constructor`); the destructor node which it later adds to every class does not tell them apart.
- Results of such a type: a function which returns, by value, a type which C++ constructs is bound as a procedure with a last parameter `Result`, a pointer to an object of the caller which the wrapper replaces by the result (`procedure greeting (Name : in ...; Result : in ...Pointer)`, called with `X'unchecked_Access`). It cannot be an Ada function: for an imported function which returns a limited type declared in another unit, GNAT expects a pointer to an existing object and copies its bits, which breaks a C++ object (an experiment with everything in one unit behaves differently, and misleads). `c_Type.is_constructed_by_Cpp` is the test at the level of the C model. The wrapper does not use the core's `result = <call>;`: it constructs a local from the call and gives it to `swig_ada_replace` (a template of `adahead.swg`), which destructs the object of the caller and move constructs (copy constructs before C++11) the local into its place, so the assignment of the class is never used. The action is one line, as an `%exception` may place `$action` within other text; where a function has an `%exception`, whose code need not hold the action and may assign to `result` itself, the `result` variable is declared too, the action notes that it has run (`swig_ada_built`), and `result` replaces the object of the caller only if it has not. One which the compiler generates is wrong for a class which manages a resource through its copy constructor and destructor alone, and gave a use after free.
- `std::string` is `swig.std_Strings.std_String`, a limited record of convention CPP with the layout of GNU libstdc++ (32 bytes on a 64 bit machine), with its array and pointer types, two constructors (`to_std_String`, from nothing or from a `char_array`) and `c_str`, `Length`, `to_Ada`, `assign` and `destruct`. These are imported from functions of the wrapper, which are a fragment of `Lib/ada/ada.swg` (`SwigAdaStdString`). `Lib/ada/std_string.i` asks for it, and so does `top` where a spec of the module needs the package (`Self.uses_std_Strings`, which the source generator sets from the context of each spec): a class with a member which is a `std::string`, in an interface which does not include that file, could otherwise not be linked (found by `./check_links`, 2026-11-22). The type has a package of its own because the record's initialisation procedure calls the C++ constructor, so whatever declares the type must be linked with those functions; in `swig` itself that would be every program.
- A function pointer type which has no typedef (`int do_op (int (*op)(int, int))`) is resolved before the unknown types are pruned, and is named by its swig type made an identifier (`p_f_int_int_ret_int`). A constant pointer to a function is left out, with a warning, when its value does not name a function of its package (`%constant int addf (int, int);`, `%callback`).
- Found by the run-time cases, and now the rule:
  - A class or structure passed by value is a pointer in the wrapper (`Ada_f (Point * a_arg1)`), as Ada passes a record to an imported subprogram by reference.
  - The `Pointer` of a virtual class is `access all Item'Class`, so that it may point to an object of a derived class and a call through it dispatches.
  - The destructor of a class which is not virtual is a function of the wrapper (`ada_destruct_<class>`), imported with convention C. Its C++ symbol cannot be made from the name of the class when that is a template instance or in a namespace. A virtual destructor is imported by its C++ symbol, which `cpp_Symbol` makes from the full name of the class (`_ZN8geometry5solid3BoxD1Ev`); for a template instance it cannot, and the old guess from the package name is used.
  - A template instance whose template has default arguments is known to the core by two names (`std::set<(int)>` and `std::set<(int,std::less<(int)>)>`); `template_full_Forms` and `template_plain_Forms` pair them, and `demand_c_Type_for` tries the pairs when a type is not found.
  - A library file declares the members of a class template with the types themselves (`size_t`, `const T&`), not with the typedefs of the class (`size_type`), as a typedef nested in a class template is not resolved and the member is then left out. It declares the destructor and copy constructor of a container, so that it is bound as a class which C++ constructs, and declares neither for `std::pair`, which is trivial where its members are, nor for `std::complex`, which is trivial: C++ returns one in registers, so a constructor which took it for a class that C++ constructs left the object as it was (found by the `library` case, 2026-11-22). The same holds for a class which is no template: `size` and `length` of `std::wstring` were left out, as they were declared with its `size_type`.
  - A static member function is a function of the package of its class, with no `Self` parameter.
  - A variable in a namespace is imported by its C++ symbol, and an integer constant of a namespace (`const int Dimensions = 2;`), which has no symbol, is given its value.
  - In the package of a class, the array type of the class is declared ahead of its pointer type, which is an instance of `interfaces.C.Pointers` and takes it. The dependency sort alone left them the wrong way round for a structure which points to itself.
  - That the destructor of a class is virtual is noted when the class is declared (`c_Type.has_virtual_Destructor`), as it is for its virtual members, so that a class derived from an imported class has a virtual destructor too.
  - `operator->`, which the core names `__deref__`, is the function `dereference`.
  - Members of a derived class: C++ lays the members which a derived class adds in the unused tail of its base class where they fit (with a base of a vtable pointer and an `int`, 16 bytes of which 4 are unused, the first new `int` is at offset 12). GNAT begins a type extension after the whole of the parent (offset 16) and rejects a representation clause which says otherwise ("position must be beyond parent"). So for a class with a virtual base class, each member which it adds is read and written through functions of the wrapper, `<member> (Self)` and `set_<member> (Self, ...)` (a member of a class type is reached by a pointer), and its record component is renamed `<member>_storage`: it reserves the storage, which is never less than C++ needs, and must not be used. `memberVariableHandler` calls the core's handler for such a member, whose `get_` and `set_` wrappers the function wrapper adds to the model (`accessor_member_Name`). An array member's function returns a pointer to its first element, and `set_` copies the whole array from one. A protected member has functions, like any protected member, which compile only where access is opened to the wrapper. A private member has none: its component is renamed like the rest, so it cannot be read at the wrong place.
  - Constructors of an abstract class: GNAT requires a CPP constructor of the parent of a type which is derived in Ada, and an abstract class cannot be constructed, so the core gives it none. `bind_constructors_of_abstract_Class` writes into the wrapper a concrete class derived from the abstract one (`ada_concrete_<class>`), with each of its constructors and a definition of each of its pure virtual functions (taken from the `abstracts` list of the class node; they call `abort` and are never reached, as Ada gives the object the vtable of its own type). Each constructor is bound to a function which constructs the concrete class in the storage it is given (`extern void ada_new_... (Shape * self, ...) { new (self) ada_concrete_Shape (...); }`). A class with a pure virtual destructor, or marked `%feature("notabstract")`, is left as it was.
  - In C, a constructor or destructor which the interface file adds with `%extend` (as `%array_class` of `carrays.i` does) is an ordinary function of the binding package, `new_<type>` (which returns a pointer) and `delete_<type>`. They were left out, so such an array could not be made. A C type is never one which C++ constructs, whatever the interface file adds to it.
  - A constructor added by `%extend` is a function of the wrapper which returns a new object. Its construction function calls it (its name is taken from the action which the core makes), copies the object and deletes it.
  - The C++ symbol of an entity is made by the package `cpp_Mangling` (`Symbol`; `cpp_Symbol` of the module body renames it), which depends on nothing else and so is tested apart from the tool (`unit/mangling`). It mangles a name within namespaces and classes, and a template instance too (`Source<(int)>` gives `_ZN6SourceIiED1Ev`), for the simpler arguments: a standard type, a class, a pointer or reference to either, a `const` one, and an integer. A part which has been written is named by its place when it recurs (a substitution: `Pair<(Shape,p.Shape)>` gives `_ZN4PairI5ShapePS0_ED1Ev`; until 2026-11-22 none was made, so such a symbol was wrong and failed when the program was linked). The standard library, whose names are abbreviated, is given no symbol. The name which swig holds for a template instance need not be the one which C++ knows it by (an argument may be a typedef, a default argument is left out, the arguments of a variadic template are a pack), so the virtual destructor of a template instance is not imported by a symbol: it is two functions of the wrapper, `ada_destruct_<class>` and `ada_delete_<class>` (which also frees the object, by `::operator delete`), imported with convention CPP as primitives of the tagged type. Each names the destructor of its own class (`self->T::~T ()`), so that it is not a virtual call: the function is itself what the vtable of a type derived in Ada holds. A destructor which is not public is still imported by its symbol.
  - Static member variables: the symbol is made from the name which C++ knows the variable by, not the one a `%rename` gives it; a variable whose type has a `std::string` in it bears the ABI tag of GNU libstdc++ (`_ZN9Structure4nameB5cxx11E`, and `_Z4nameB5cxx11` for one in no namespace; `variable_Suffix`); one which `%extend` adds is a pair of functions and no variable, and is left out with a warning; and a constant with a value is given it where it is an integer, a real number, a `bool`, a `char` (`interfaces.c.char'Val (65)`) or of an enumeration (by its number, `Mode'Enum_Val (5)`, which is sought among the literals of the type), `constexpr` counting as constant.
  - `typemaps.i`: a parameter with an `INPUT` typemap is passed by value, which the typemap says by the attribute `byvalue` (`%typemap (in, byvalue="1")`, read as `tmap:in:byvalue` in `to_c_Parameters`). Until 2026-11-22 the wrapper took the value and the spec gave a pointer. `OUTPUT` and `INOUT` parameters are pointers.
  - A class which is used before it is declared (a template instance ahead of its `%template` line, as a header which is included first has it): `demand_c_Type_for`, asked for a pointer or reference to a type which is not known, makes the type itself, not known, with its pointer and array types (`register`), and not the pointer alone. When the class is declared, `make_the_Class` of the class handler makes that type the class, under the name by which the class is bound (the name of its `%template`, not one made from its arguments), and names the types which were made with it after it. An instance may have been used by its name with the default arguments of its template given (`Two<(int,long)>` for `Two<(int)>`), so that form is sought too, and the pairs of `template_full_Forms` are tried both ways. Until 2026-11-22 a function which took or returned such an instance was left out.
  - A base class which has a function that returns a pointer to its derived class (`class Leaf; class Node { Leaf* as_leaf (); }; class Leaf : public Node`): the package of the base has a limited view of that of the derived class, and the result is `access foo.Leaf.Item'Class`, as is a parameter which is a pointer to the derived class. `is_mutually_dependent` counts a class which is derived from a class that is declared in this package, and the dependence of a record on a package counts its base classes. Only such a base class is looked for: a wider test (whether the other class depends on this package at all) took for a cycle what is none, and gave the functions of cBound's `fann` an anonymous access parameter in place of `fann.Pointer`, which the suite's baseline showed and cBound's demo caught. Before, each spec needed the other and neither compiled.
  - Global variables: one which is `static`, or in C++ constant (an array of constants too) and not `extern`, has no symbol outside its file. It is given its value where that is worked out (an integer, a real number, a `bool`, a `char`), and is otherwise left out with a warning. A variable is imported by the name which the library knows it by, not the one a `%rename` gives it, and a variable of the standard library by its abbreviated symbol (`std::cout` is `_ZSt4cout`).
  - A constant whose value is a string of no characters (`#define EMPTY ""`) is marked so (`is_empty_String` of `c_Variable` and `ada_Variable`), as its value cannot be told from no value: it was bound as a variable which imported a symbol that does not exist, in the tool's own binding of the swig core too.
  - A `bool` is one byte on both sides: its `ctype` is `unsigned char` (it was `unsigned int`, of which Ada set one byte), and `swig.bool` is `interfaces.C.plain_char`.
  - A class whose destructor is hidden has no `construct` function in its spec, as it has no construction function in the wrapper to import.

Ada has no class within a class, so the module says so to the core (`nestedClassesSupport` returns `NCS_None`), which then moves each nested class out as it does for one marked `%feature ("flatnested")`. What is within a template is passed over, as it is seen again in each instance. A nested class with no name is still bound by the module itself: the parser keeps it where `cparse_keep_unnamed_nested` is set (a local change to `parser.y`, which `main` of the module sets).

C++ has one virtual function, that of all its arguments, so only that one is virtual in Ada (`new_c_Function`, by the attribute `defaultargs` of the others): each of the others is a function of the class-wide type, whose function of the wrapper makes the virtual call. Until 2026-11-23 each was a primitive with a place of its own in the vtable, so that every virtual function after it was out of its place: a dispatching call from Ada reached another function, and a function which was overridden in Ada was called by C++ in place of another. The tool's own binding of `Language` had five such functions (`addSymbol`, `symbolLookup` and others), and an override of anything declared after them was not called, which is how this was found.

The transformer already held the place of one whose types are not known (`unbound_virtual_<n>`). The core does not hand on a virtual function which the interface file ignores, one which is deleted (`= delete`), or a virtual destructor which is not public, so `add_hidden_Virtuals` walks the members of the class ahead of each member function and destructor, and at its end, and adds a function which only holds the place (`c_Function.is_Placeholder`) for each such member that it passes, in its place among the others; a virtual overload which Ada cannot tell from another is given one where it is left out. The two places of a destructor which is not public are named `destruct_0` and `destruct`, so that the destructor of a derived class, which may be public, overrides them; like any place holder they are not to be called. A function which overrides needs no place of its own. A function which `%extend` adds is no member of the class: it is never virtual, and neither overrides nor is overridden.
    - A base class which the interface file ignores (`%ignore Base;`) is bound for its shape alone, where a class which is bound is derived from it. The core does not hand on an ignored class, so the class which is derived from it lost the members and the virtual functions of its base: its record was too small, and its virtual functions out of their places (a warning said that the base was not known). Where the element type is not known as an array type (or a dimension is unknown), a member is one dimension of the whole length. Before this a structure with such a member was left out altogether, with every function which used it.
  - A reference to a pointer (`int*&`) is a pointer to the pointer.

  - A pure virtual conversion operator (`virtual operator Other () = 0;`) is defined in the concrete class of an abstract class with no result type.

A member of a C structure is therefore placed by the line on which it is declared (`c_Variable.Line`, `c_Type.add_Component_in_Order`); before, the record had those members last, where C has them in their place.
  - A parameter with no name is `arg_1` where it is the only one, and `arg_<place>` otherwise (`makeParameterName`), in the spec and in the wrapper alike; two of them were given one name in a construction function, and `arg_2_1`, `arg_2_2` in a spec.
  - The name of a construction function is made unique by `wrapper_Symbol`, as two constructors which are protected are in no overload chain and so are given no suffix by the core. The concrete class of an abstract class is constructed with the parameters as they are named (`plain_call_Args`), and its definition of a pure virtual function keeps the reference qualifier and the `noexcept` of the function; a class with a pure virtual function which is `final` has no concrete class.
  - A constructor template of which `%extend` names an instance (`%extend C { %template (C) C<int>; }`) is a constructor of the class, not a function of the wrapper.
  - Where a function which returns a class or structure by value fails with an exception pending (`SWIG_exception`, a contract), it returns bytes of zero (`swig_ada_no_result` of `adahead.swg`, or a compound literal in C).
  - A variable which differs only in case from a class of its package (`a` and `A`, which has a child package) is prefixed `the_`.
  - A package which declares a subtype of a type of another package (`typedef Element* element_ptr_t;`) is given the whole of that package, not a limited view, which a subtype declaration cannot use (`ada_Context.to_Source`).
  - A member which is a pointer to a type declared later in its own package (`Element** selfptr;` in `Element`, whose `Pointer` follows its record) is a `system.Address`.
  - The wrapper defines `SWIG_VERSION` and `SWIGADA` (`Swig_obligatory_macros`), as the wrapper of every other language does, and `$isvoid` is 1 in the wrapper of a function which returns nothing.
  - An enumeration which names its underlying type (`enum Small : unsigned char`) is given the size of that type (`for Small'Size use 8;`), taken from the `inherit` attribute of its node, so that it is laid out as C++ has it in a structure. The wrapper casts an enumeration result to `int`, which a scoped enumeration (`enum class`) requires.
  - Bit-fields: GNAT does not lay bit-fields out as C does, so for a record which has one, the source generator works out the place of every component (`laid_Out`, by the rules of the System V ABI: a bit-field does not cross a unit of its own type, one of no width ends the unit, and the type of one with no name does not align the record) and writes a full record representation clause (`<member> at 0 range <first bit> .. <last bit>;`), with the size and alignment of the record. A bit-field component is not aliased, and has the range which its bits allow. The sizes of the C types are those of the generating machine (`size_by_Name`); a type extension is left to GNAT (its members are reached by functions), and a class with a member whose size is not known is not laid out, with a warning. A class with virtual functions and no base begins after its vtable pointer. Before this, bit-fields were not carried from the C model to the Ada one at all, and each was a whole `unsigned`.
  - Layout of derived classes with no virtual functions: C++ places the members of a derived class (and its further base classes) in the unused tail of a base class, unless that base is a plain structure ("POD for the purpose of layout"). GNAT places a component after the whole of the one before, so `class Derived : public Base` with `Base { int i; char c; Base (); }` had its first member at offset 8 where C++ has it at 5. The class handler notes on the class (`c_Type.is_layout_Pod`, carried to the Ada record) whether it is such a plain structure, by the cases in which GCC uses the tail (measured, not taken from the standard): it declares a constructor, a destructor, a copy constructor or an assignment operator which is not defaulted; it has a member variable which is not public, or which has an initial value; it has a base class; or it has a virtual function. A member of such a type, or an array of them, makes its class one too (`is_plain_Structure` of the source generator). The constructors and destructor which the core adds itself (`default_constructor`, `copy_constructor`, and a destructor where the class has no `allocate:has_destructor`) do not count.
  - The layout engine (`laid_Out`) gives each base class component the size it takes as a base: all of it for a plain structure, all but the tail (`data_Size`) for any other, and nothing for a class with no members. Where that is less than the size of its type (`needs_Layout`), the record has a representation clause, and that base is storage alone, `<base>_storage : interfaces.C.char_array (1 .. <bytes>)`, since a component of its type would lie over the members which follow (and is left out where it takes nothing). The base is reached by `as_<base>`, which every class now has for each base class which is not its parent, not only a class with a parent. A base whose tail is not used stays a component of its type (`the_Plain.Plain.i`). A type extension is still left to GNAT, with its members reached by functions.
  - Layout checks (`layout_Checks` of the source generator, written into the wrapper file after the specs are made): for a class whose record is laid out here, the wrapper asserts when it is compiled that the class has the size, and each public member the place, which the record takes it to have (`static_assert`, or `_Static_assert` in C, of `sizeof` and `offsetof`, through the macro `SWIG_ADA_LAYOUT_CHECK`, which is empty for a compiler older than C++11 or C11). A record which does not match its class then does not build. This is done for every class whose layout can be worked out (the default since 2026-11-21, after some 4,750 assertions over the suite, xcb and gmp had given no false alarm). With `-no-check-layout` only a class with a representation clause is checked, as that layout is for the generating machine (an option cannot begin `-l`, which the core takes for a library file), and a compilation which defines `SWIG_ADA_NO_LAYOUT_CHECKS` leaves the checks out altogether. Not checked: the place of a member whose name begins `__`, which belongs to the implementation and may differ where the wrapper is compiled (glibc gives six members of `struct lconv` such names unless `__USE_ISOC99` is defined, which the core does not define); a type extension; a class with no members; a class which cannot be named in the wrapper (private, or with no name); the members of a standard library class, which a library file names for itself; a bit-field; a base class; and a record which is known to have lost something (`has_lost_Layout`: a base class or member which could not be bound, an ignored member of unknown type, a member of a class which is declared and never defined, a virtual base class of a class with virtual functions). Each of those is warned of.
  - Found by checking every class of the test suite: a function of the class which a smart pointer points to is no virtual function of the smart pointer (a smart pointer to a class with virtual functions was a tagged type, with its members after a vtable pointer which C++ does not have); a base class is sought by its full name before its plain name (`A::C::Foo`, where `A::B::Foo` is declared too); and `SWIGWORDSIZE64` is defined on a 64 bit machine, which the library's `stdint.i` needs to give `int_fast16_t` and its like the size of `long`.
  - Nested classes and unions with no name, in C++ (`bind_unnamed_nested_Classes`, called by the class handler before the class is made current): the core leaves such a class out, and the members declared with it. Each is given a class of its own from the node which the parser keeps, named `<outer>_<member>` as the core names one in C (`Variant_val` for `union { ... } val;`), or `<outer>_anonymous_<n>` where no member is declared with it, as for an anonymous union. Its members are made from their declaration nodes (`member_Variable`), and those nested within it likewise. `add_hidden_Members` then gives the outer class a member for each declarator, in its place among the others: the class itself, a pointer to it or an array of it, or `anonymous_<n>` for an anonymous union, whose members C++ takes as members of the outer class and which Ada reaches as `the_Variant.anonymous_3.i`. In the wrapper the class is named `decltype (<outer>::<member>)` for its layout check. `ada.swg` silences the core's warning 312, which says that such a class is ignored. This is so with `%feature ("flatnested")` too: the parser keeps and discards a class with no name whether or not nested classes are flattened, as flattening lost the members declared with it and took the members of an anonymous union for members of the outer class, one after another. A nested class which a typedef names is still flattened.
  - Hidden members (`add_hidden_Members`, called ahead of each member variable and at the end of the class): a bit-field with no name is a component which is given no declaration and only takes part in the layout; a member variable which the interface file ignores (`%ignore Sensor::state;`) is a component `<member>_storage`, as without it every member after it was out of place and the Ada object was smaller than the C++ one. Where the type of an ignored member is not known, its storage is given up with a warning, in the prune step, so that the class is still bound.
  - `long double` is `interfaces.C.long_double`. It was not a known type, so a structure with such a member was left out.
  - A static member variable is a variable of the package of its class (`Counter.total`), imported by its C++ symbol, which `cpp_Symbol` makes from the name of the class (`_ZN7Counter5totalE`; in a namespace or a simple template instance too, and left out with a warning where it cannot). A constant integer or real number with a value in the class (`static const int limit = 16;`) need have no symbol, and is a constant with that value. A private or protected one is not bound, nor one whose class is not bound. `c_Variable.owner_Class` names the class, and the transformer adds the variable to its package.

- Type descriptors of the swig runtime: Ada has no table of types, but a typemap written for another language may name a descriptor (`$descriptor`, `SWIGTYPE_p_Foo`) and convert through one. `adahead.swg` declares a minimal `swig_type_info`, with `SWIG_ConvertPtr` and `SWIG_NewPointerObj` which give the pointer back as it is, and `top` declares in the header each descriptor which the wrapper names.

Where the element type has no default constructor the container is empty and an exception is left pending; before, the wrapper of such a container did not compile.

The forward declaration is registered by the full name (`Swig_symbol_qualified` gives the scope), and under the name it is bound by (its `sym:name`, as a `%rename` may differ: `TagLib::FLAC::File` as `FLACFile`). Such a function could not be overridden in Ada before: C++ calls through the vtable with the arguments where its ABI has them, the hidden pointer to the result first on x86-64 and in a register of its own on AArch64, and putting `Result` first in the profile of a primitive, which is right on x86-64 alone, was rejected. The override must be in C++: GNAT takes the vtable of a type which is derived from a C++ type from the C++ class itself, when the type is elaborated, and not from what the spec imports for each place (a first form which only imported the override, a free function, for the place holder of the function, was found to change nothing). (`./check_vtables` took a parent of a type extension by `.Item`, which the pretty printer writes, where the generator writes `.item`, so that in the folder of a run-time case, whose specs are not pretty printed, no type extension was compared with its parent's places; it now ignores case, and the classes of `directors`, `virtual_bases`, `leveldb`, `pugixml` and `taglib` agree with the compiler.) `./check_vtables` compares the type of a director with its class in C++ (named in the wrapper by the comment before it), and the `directors` run-time case calls every kind of such function, overridden and not, from C++.
- `foo-<class>_pointer.ads` — for a class whose pointer type is a plain access type (one which C++ constructs, or which is virtual or abstract: `access all Item` or `access all Item'Class`), the package `foo.<class>_Pointer`, which declares that type with a limited view of the package of the class, and of which the `Pointer` of the class is a subtype (`pointer_Package` and `emit_pointer_Spec` of the source generator; 2026-11-25). Any package may have the whole of it without a cycle, so a function of a package which has only a limited view of the class returns `foo.<class>_Pointer.Pointer`, where it returned an anonymous access type (`access foo.Node.Item'Class`), whose result GNAT 16 does not let be converted to a named pointer type at run time, as its accessibility is that of the caller (jsoncpp had 48 such functions, tinyxml2 28). A parameter through a limited view is left an anonymous access, which takes the `'Access` of an object which a subprogram declares, where a named type would not. An override writes each as the function which it overrides does (`origin_Package`); a subtype of the one type statically matches it. The name is given a number where a package of the modules has it already (`smart_pointer_inherit` has a class `ItkVectorContainerUILSNUS2_Pointer` beside `ItkVectorContainerUILSNUS2`, whose pointer package is then `..._Pointer_2`). A program which compared such a result with `null` needs a `use type` of the pointer type now, as an anonymous access type had its equality visible everywhere (`mutual_classes`' tester). The tool's own binding has two (`swigmod.Language_Pointer` and `swigmod.Dispatcher_Pointer`).
- `foo-<class>-guards.ads` — for a C++ class with a virtual destructor, an instantiation of `swig.Guards`. GNAT never calls a C++ destructor by itself, so a `Guards.Guard (the_Object'Access)` declared after the object calls it (via the non-deleting `destruct_0`) when the guard leaves scope. For a virtual class, `destruct_0` is the complete object destructor (`D1`) and `destruct` the deleting destructor (`D0`), which also frees the object; `destruct` is therefore only for an object allocated by C++ `new`, never for an Ada stack object or one allocated by an Ada allocator. A class whose destructor is not virtual has no deleting variant, and there both import `D1`.

## Conventions

- **Ada formatting follows the lace house style, as set out in `/eden/forge/applet/tool/ada_formatting_guide/`** (prose chapters in `guide/NN-topic.md`, a compilable reference corpus in `examples/src/`). Read the relevant chapter before writing or reformatting Ada here — at the least `01-layout.md`, `02-naming.md` and the chapter for the construct in hand (`03-declarations`, `04-statements`, `05-subprograms`, `06-packages`, `07-comments`, ...). The essentials:
  - 3 space indent; `is`, `then` and `loop` on a line of their own; named `end`s; no enforced line length.
  - Adjacent related lines are hand padded into shared columns (`:`, mode, type, `:=`, parentheses, `return`); a blank line ends an alignment group. Three spaces (the "wide gap") join elements deliberately sharing a line, e.g. `(Self : access Item;   N : in Node_Pointer)`.
  - Casing is by head word: the dominant word of a compound name takes the capital and the rest stay lower case (`ada_Language`, `c_Type`, `swig_Module`, `is_Ignored`, `to_ada_Variable`); a name which is a single verb is lower case (`define`, `transform`, `log`); root packages are lower case as a prefix (`ada.Strings.unbounded`, `interfaces.C`).
  - Packages are classes: principal type `Item`, with `View` (`access all Item'Class`), written `.item`/`.view` in dotted cross-package references (`c_Type.view`, `ada_Language.item`).
  - **Never run `gnatpp` (or any formatter) on the hand written sources** — it cannot produce this style and destroys the column alignment. The `gnatpp` calls in the `builder` scripts and the test suite are for *generated* binding specs only.
  - This applies to hand written Ada (`Source/Modules/ada/*.ad?`, `ada_type/`, `tester.adb`s, `launch_testsuite.adb`), not to generated files (`swig_binding/**`, the specs emitted into `Examples/ada/*`).
  - The guide's machine checkable subset is `-gnaty3befhiklOx`; `swig_applet_ada.gpr` currently enables a slightly different set (see above), so a clean compile is not proof of conformance.
- **Ada coding style (substance, as opposed to presentation) follows the rule based guide in `/eden/forge/applet/tool/ada_style_guide/guide/`.** It covers naming choices, comments, structure, types, statements, subprograms, exceptions, concurrency, portability, reusability, OOP and modern Ada, as rules with stable IDs (`NAM-06`, `STM-07`, ...). `rules-index.md` lists every rule on one page; consult it, then the full entry in the numbered file, when writing new Ada. For a review or clean-up of existing code follow `00-procedure.md` (inventory, profile, detection, report, apply).
  - Each rule has an apply level: `auto` (exact and semantics preserving; make it, then rebuild), `assisted` (make it when confident, otherwise propose it), `advisory` (design level; report it, never apply unasked).
  - The two guides divide the ground: the formatting guide owns presentation (indentation, alignment, casing, spacing, blank lines) and is this project's written standard, so it wins wherever the style guide contradicts it. Such rules go on the procedure's overrides list and are never applied `auto` — for the lace style these are `STM-01`, `STM-02`, `COM-07`, the generic instantiation clause of `SUB-02`, `TYP-04`, and the pragma-to-aspect conversions of `MOD-12` and `POR-01`. `NAM-06`, `NAM-12`/`OOP-07` and `COM-03` are also in tension with it (type suffixes and plural array types, constructor naming, comment placement).
  - The sources are compiled as Ada 2022 (`-gnat2022` in `ada-build/swig_shared_library.gpr`), so all the `MOD` rules of `14-modern-ada.md` are available. Two consequences of Ada 2022 to keep to: array aggregates are written with square brackets (`[1 => X]`, `[others => ' ']`; the parenthesised form draws an obsolescence warning), and a record aggregate passed to a container's `append` must be qualified (`append (the_Elements, an_Element'(Kind => Value, ...))`), as it is otherwise ambiguous with a container aggregate.
  - The style guide's Detect patterns are written in Reference Manual casing; run them case insensitively here (`grep -i`), as this code uses head-word casing.
  - Exclude the generated files (`swig_binding/**`, emitted example specs) and the upstream SWIG sources from any review.
- The user manual of the Ada module is `Doc/Manual/Ada.html`, a chapter in the form of those of the other languages (listed last in `Doc/Manual/chapters`, so that no other chapter is renumbered; `python3 maketoc.py` in that directory numbers its headings and makes its index and `Contents.html`, and leaves `.bak` files to be removed). It is what a user of a binding reads; this file is the design record. A change to how a construct is bound belongs in both.
